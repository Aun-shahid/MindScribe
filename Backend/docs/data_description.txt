# 4.1 DATA DESCRIPTION

## 4.1.1 Introduction

This section describes how the information domain of the MindScribe therapy session management platform is transformed into persistent data structures. The data design follows established software engineering principles for relational database modeling, ensuring data integrity, normalization, and efficient query performance while supporting the complex relationships inherent in a mental health therapy management system.

## 4.1.2 Database Management System

### Primary Database: PostgreSQL

MindScribe employs **PostgreSQL** as its primary relational database management system (RDBMS). The database configuration is managed through Django's ORM (Object-Relational Mapping) with support for dynamic configuration via environment variables and the `dj_database_url` package for streamlined deployment across different environments.

```python
DATABASES = {
    'default': dj_database_url.config()
}
```

**Configuration Parameters:**
- **Database Name:** MindScribe
- **Database User:** postgres
- **Host:** Configurable (localhost for development, Railway for production)
- **Port:** 5432 (PostgreSQL default)

PostgreSQL was selected for the following technical advantages:
1. **ACID Compliance:** Ensures transactional integrity for sensitive healthcare data
2. **JSON/JSONB Support:** Native support for semi-structured data (emotion scores, metadata)
3. **UUID Support:** Native UUID data type for globally unique identifiers
4. **Scalability:** Horizontal and vertical scaling capabilities for production workloads
5. **Security:** Advanced authentication, encryption, and access control mechanisms

## 4.1.3 Storage Organization

The MindScribe system employs a **relational database structure** organized into logical modules, each encapsulating domain-specific entities. The storage architecture follows Django's application-based modular design pattern:

### Module Organization

| Module | Purpose | Primary Tables |
|--------|---------|----------------|
| **users** | User identity, authentication, and profile management | users, patient_profiles, therapist_profiles, connection_requests |
| **therapy_sessions** | Session scheduling, management, and tracking | sessions, therapist_availability, therapist_date_overrides, session_templates, session_reminders |
| **transcription** | Audio transcription and emotion analysis | transcriptions, transcription_segments, emotion_analysis, realtime_transcription_sessions, mood_snapshots |
| **history** | Patient progress tracking and self-monitoring | mood_entries, journal_entries, activity_logs, medication_logs, sleep_logs, symptom_tracker, coping_strategies |
| **soap** | Clinical documentation and SOAP notes | soap_notes, soap_note_versions, soap_templates |
| **core** | System-wide utilities and audit logging | audit_logs, system_configurations |
| **authenticator** | Token-based authentication management | password_reset_tokens, email_verification_tokens, refresh_tokens |

### Primary Key Strategy

All major entities utilize **UUID (Universally Unique Identifier)** as primary keys instead of auto-incrementing integers. This design decision provides:
- **Global Uniqueness:** Prevents key collisions in distributed systems
- **Security:** Non-sequential IDs prevent enumeration attacks
- **Merge Compatibility:** Facilitates data migration and synchronization

## 4.1.4 Major Entities and Relationships

### 4.1.4.1 User Domain Entities

#### User (Extended AbstractUser)
The central authentication entity extending Django's AbstractUser with healthcare-specific attributes. Serves as the foundational entity for role-based access control.

**Relationships:**
- **One-to-One** with PatientProfile (for patient users)
- **One-to-One** with TherapistProfile (for therapist users)
- **One-to-Many** with Session (as patient and as therapist)
- **One-to-Many** with various tracking entities (mood entries, journal entries, etc.)

#### PatientProfile
Extended patient information including therapy preferences, medical history, and therapist connection details.

**Relationships:**
- **One-to-One** with User
- **Many-to-One** with TherapistProfile (assigned therapist)
- **Many-to-One** with TherapistProfile (created_by_therapist)
- **Self-referential** via original_therapist_patient (for account merging)

#### TherapistProfile
Professional information for therapist users including licensing, specialization, and practice details.

**Relationships:**
- **One-to-One** with User
- **One-to-Many** with PatientProfile (patients)
- **One-to-Many** with ConnectionRequest

#### ConnectionRequest
Manages the patient-therapist connection workflow with status tracking.

**Relationships:**
- **Many-to-One** with User (patient_user)
- **Many-to-One** with TherapistProfile
- **Many-to-One** with PatientProfile (merged_with_patient)

### 4.1.4.2 Therapy Session Domain Entities

#### Session
The core entity representing therapy sessions with comprehensive tracking of scheduling, content, and outcomes.

**Relationships:**
- **Many-to-One** with User (patient)
- **Many-to-One** with User (therapist)
- **Many-to-One** with User (cancelled_by)
- **Many-to-One** with User (created_by)
- **Self-referential** via recurrence_parent (for recurring sessions)
- **One-to-One** with SessionQRCode
- **One-to-One** with SessionInsight
- **One-to-Many** with SessionAudio
- **One-to-Many** with SessionReminder
- **One-to-Many** with MoodSnapshot

#### TherapistAvailability
Weekly recurring availability configuration for therapists.

**Relationships:**
- **Many-to-One** with User (therapist)

#### TherapistDateOverride
Specific date exceptions to regular availability (holidays, vacations).

**Relationships:**
- **Many-to-One** with User (therapist)

### 4.1.4.3 Transcription Domain Entities

#### Transcription
Session transcription metadata and processing status.

**Relationships:**
- **One-to-One** with Session
- **One-to-Many** with TranscriptionSegment

#### TranscriptionSegment
Individual speech segments with speaker identification and timing.

**Relationships:**
- **Many-to-One** with Transcription
- **One-to-One** with EmotionAnalysis

#### EmotionAnalysis
AI-generated emotion analysis for transcription segments.

**Relationships:**
- **One-to-One** with TranscriptionSegment

#### RealtimeTranscriptionSession
Manages active real-time AI transcription streams.

**Relationships:**
- **One-to-One** with Session
- **Many-to-One** with Transcription

### 4.1.4.4 History/Progress Tracking Domain Entities

#### MoodEntry
Patient self-reported mood and contextual tracking.

**Relationships:**
- **Many-to-One** with User (patient)

#### JournalEntry
Personal journaling with emotional context.

**Relationships:**
- **Many-to-One** with User (patient)

#### PatientGoal
Therapy goals with progress tracking.

**Relationships:**
- **Many-to-One** with User (patient)
- **Many-to-One** with User (therapist)
- **One-to-Many** with PatientMilestone

### 4.1.4.5 SOAP Notes Domain Entities

#### SOAPNote
Clinical documentation following the SOAP (Subjective, Objective, Assessment, Plan) format.

**Relationships:**
- **Many-to-One** with User (patient)
- **Many-to-One** with User (therapist)
- **Many-to-Many** with Session
- **One-to-Many** with SOAPNoteVersion

## 4.1.6 Database Indexing Strategy

The system implements strategic database indexes to optimize query performance:

### Composite Indexes
- `therapist_date_idx`: (therapist, scheduled_date) - Optimizes therapist schedule queries
- `patient_date_idx`: (patient, scheduled_date) - Optimizes patient session history
- `status_date_idx`: (status, scheduled_date) - Optimizes status-filtered queries
- `therapist_status_idx`: (therapist, status) - Optimizes connection request queries

### Single-Column Indexes
- `patient_id_idx`: patient_id - Fast patient lookup
- `linked_account_idx`: is_linked_account - Account linking queries
- `emergency_idx`: is_emergency - Emergency session filtering
- `expires_at_idx`: expires_at - Token expiration queries

## 4.1.7 Data Integrity Constraints

### Check Constraints
- `min_duration`: Session duration >= 15 minutes
- `max_duration`: Session duration <= 480 minutes (8 hours)
- `valid_mood_before`: Mood rating between 1-10 or null
- `valid_mood_after`: Mood rating between 1-10 or null
- `valid_effectiveness`: Effectiveness rating between 1-10 or null
- `valid_session_frequency`: Session frequency in allowed values

### Unique Constraints
- `unique_pending_request`: Prevents duplicate pending connection requests per patient-therapist pair
- `unique_therapist_date_override`: One override per therapist per date
- Email uniqueness on User model
- License number uniqueness on TherapistProfile
- Therapist PIN uniqueness on TherapistProfile

## 4.1.8 Soft Delete and Audit Trail

The system implements comprehensive audit logging through the `AuditLog` model:
- Tracks all CRUD operations (Create, Read, Update, Delete)
- Records user, timestamp, IP address, and user agent
- Stores change details in JSON format
- Enables compliance with healthcare data regulations

## 4.1.9 Data Transformation Structures

Key serializers transform database models into API representations:

| Serializer | Purpose |
|-----------|---------|
| SessionSerializer | Full session details with computed fields |
| PatientSessionSerializer | Patient-centric session view with appointment labeling |
| TherapistSessionSerializer | Therapist management view with action options |
| MoodEntrySerializer | Mood tracking with trigger parsing |
| JournalEntrySerializer | Journal entries with tag handling |
| SOAPNoteSerializer | Clinical documentation formatting |

## 4.1.10 Conclusion

The MindScribe data architecture provides a robust, scalable foundation for managing therapy sessions, patient progress, and clinical documentation. The modular design allows independent scaling of components, while the comprehensive relationship model ensures data integrity across the healthcare workflow. The PostgreSQL backend with Django ORM provides the reliability and security required for sensitive healthcare data management.
